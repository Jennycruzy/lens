Integrate

Three ways in.

Every read carries a freshness bound; there is no version without one. Copy a snippet, resolve the chain key for your environment, choose a bound from what the value means.

Inherit LensConsumer. Resolve sourceKey from Creditcoin's ChainInfo for the environment you deploy to — chain keys are local to one environment, so never copy one from an example.


        

      

      

        
LensAggregatorV3 exposes an eligible Lens feed through the familiar AggregatorV3Interface, so contracts already written against it can consume slow-moving or time-averaged cross-chain state with minimal work. For that class of state only — not block-sensitive spot pricing or fast liquidations. A value whose original source is Chainlink keeps Chainlink's own trust assumptions; Lens removes the need for a trusted cross-chain reporter.

        

        

      

      

        
The SDK takes native chain ids and resolves Attestcoin chain keys for the current Creditcoin environment. It refuses explicitly and lets you re-check the bytes yourself.

        

        

      

    

  





  

    
Choosing a bound
Pick it from what the value means.

    

      
Feed classSuggested boundWhy

      
        
30-minute observation / TWAP inputs150–300 blocksthe average already spans longer than the lag

        
Liquid-staking rate600–2400 blocksmoves basis points per day

        
Reserves, supply600–1800 blockscheckpoints, not ticks

        
Governance weight at a snapshot5000+ blocksthe snapshot block is fixed; only the proof's age matters

        
Access lists, pause flags300–900 blockschange deliberately and rarely

      
    

    
Any bound below about 50 can never be satisfied: the frontier trails the head by 30–40 blocks. Never widen a bound to make a revert go away — the revert is the feed saying it no longer describes what you think it does. Full guide: docs/INTEGRATING.md.
